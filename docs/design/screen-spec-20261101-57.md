## 구현에 반영할 결정과 열린 문제

### 1. 상품과 공구를 분리한다

`Product → Variant → Campaign`을 구분한다. 상품 설명·고지·후기·공통 문의는 상품에, 모집 인원·일정·조건·공구 질문은 회차에 연결한다. 품목이 다른데 동일한 고지 양식을 강제하지 않는다. KC 등 안전 확인은 실제 적용 품목·근거를 확인하며 이미지 속 ‘정보 확인 중’을 인증된 사실로 바꾸지 않는다.

### 2. 주문 상태와 모집 상태를 구분한다

`결제 대기 → 결제 확인 → 유효 참여`와 `모집 중 → 마감 판정 → 성사/미달`은 다른 상태다. 환불도 요청·처리 중·완료·실패를 나눈다. 외부 결제 요청은 DB 트랜잭션 안에서 대기하지 않고, 검증된 웹훅과 멱등 키로 주문·원장·참여를 반영한다. 동일 사용자의 수량이 많아져도 참여 인원을 늘리지 않는다.

화면 07의 행사 종료와 모집 마감은 모두 11/02 18:00이다. 화면의 예시 날짜를 운영 데이터로 복사하지 않고 서버의 회차별 기한을 표시한다. 향후 행사 기간과 모집 기간이 달라지면 가격 적용 조건을 별도로 정의해야 한다. 화면 04의 18명→화면 23의 19명은 예시 전환이며 운영 실적이 아니다.

### 3. 기존 요구를 새 탐색 구조에 연결한다

추천하는 탐색 배치는 설계서의 하단 5메뉴를 따르고, 홈 상단에 브랜드관·핫딜 모음, 마이에 쿠폰·마일리지를 두는 것이다. 이는 **배치 제안**이다. 원본 화면이나 메뉴를 이미 변경한 것으로 기록하지 않는다. 타임세일은 자체 공구의 기간 행사, 핫딜 모음은 외부 정보 중계이므로 같은 필터로 섞지 않는다.

### 4. 베타와 실거래 문구를 구분한다

현재 베타에서 주소·대표자 생년월일·사업자서류·결제정보를 받지 않는다. 설계서의 ‘결제 완료’, ‘자동 환불’, ‘배송 준비’, 구매 인증 별점은 실제 처리 연결 전까지 운영 사실로 표시할 수 없다. 테스트 모드에서는 ‘시험 참여’임을 표시한다. 이는 기능 범위를 없애는 결정이 아니라 실제 서비스 전환 전 필요한 조건이다.

### 5. 검증 순서

1. 공구 인원·조건 버전·마감 판정·상품/옵션 계약을 먼저 확정한다.
2. 새 탐색 메뉴와 상품 상세 4개 탭, 브랜드/기획전/핫딜 진입을 연결한다.
3. 독립 커뮤니티의 공개 읽기·작성 권한·신고·차단·삭제를 구현한다.
4. 허가된 PG 시험환경에서 개별/공구 결제·취소·미달·중복웹훅·포인트 복원을 검증한다.
5. 실제 Android 설치·HTTPS·게스트→로그인 복귀·재시도·운영자 처리까지 확인한다.

새 설계서 검토는 배포 준비와 병행한다. 전체 화면 구현 완료, 실제 결제 가능, 외부 베타 공개 가능을 각각 증거로 판단한다.

## 대조 근거

- `frontend/src/main.tsx`: 현재 경로·하단 메뉴·로그인 필요 화면.
- `frontend/src/catalog.tsx`: 공구 상세·가격·배송정책·질문·신고·예약 수량.
- `backend/app/main.py`: 공구/예약/신청/쿠폰/질문/신고 API. 독립 상품·커뮤니티·PG 주문 API는 없음.
- `backend/app/db.py`: User/Token/RateBucket/Record와 SQLAlchemy 트랜잭션. 도메인별 상품·주문 테이블 정리는 후속 작업.
- `backend/app/schemas.py`: 현재 신규/재설정 비밀번호 최소 10자. 설계 13번의 12자 안내와 다르다.
- [이전 화면 대조](screen-spec-v0.6.md)와 [베타 QA](../build/beta-20261101/QA.md): 기존 확인 결과. 새 화면의 성공 증거로 대신하지 않는다.
