사용자는 관심 있는 육아템이나 질문을 찾고, 조건을 비교한 뒤, 챗봇이나 댓글로 궁금한 점을 확인합니다. 확인한 정보는 저장하고 경험을 남길 수 있습니다. 차별화 가설은 제품 조건과 사용자 경험, 공식 근거를 하나의 동선에서 확인하는 데 있습니다. 서비스는 정보와 공동구매 수요를 연결하고 주문·결제·배송·환불은 판매처에서 처리합니다. 관련 요구사항은 groupbuy_02, demand_01~05, comment_01, save_01입니다.

## 4. 제공 데이터의 발견과 서비스 적용 · 45초

제공 자료는 네 종류입니다. 소비자 자료는 비교 기준의 선택권을 설계하는 참고로 썼고, 육아용품 표본 41명이라는 범위를 확인했습니다. 소매 데이터는 파일이 달라도 541,909행이 중복되어 추가 합산에서 제외했습니다. 거래 자료의 동시 출현 분석은 현재 서비스의 함께 저장한 육아템 집계에 적용했습니다. 종료된 쇼핑 세션은 분류 실험에 사용하고 실제 서비스에서는 사용자가 선택한 기준에 따른 CTA와 측정 구조를 구현했습니다. 서로 다른 자료를 같은 회원으로 연결하는 키는 없습니다. 근거 docs/reports/data-use-20261103/REPORT.md, ai-pipeline/artifacts/overlap_audit.json.

## 5. 연관 분석 실험과 공동 저장 집계 · 50초

연관 분석은 시간순으로 나눈 과거 거래에서 평가했습니다. 상위 100개 품목을 두 개 이상 가진 평가 송장 4,338개에서 품목 하나를 숨기고 상위 다섯 개 추천에 복원되는지 봤습니다. 조건부 Recall@5는 인기순 10.56%, 연관 규칙 36.21%였습니다. 이 결과의 적용 범위는 해당 과거 장바구니 복원 실험입니다. 서비스에는 동시 출현 방법을 옮겨서, 회원별 저장 중복을 제거하고 다섯 계정 이상이 함께 저장한 조합을 운영자에게 제공합니다. 운영자는 이 조합을 비교 가이드와 공구 조사에 활용합니다. 실제 육아 이용자의 구매 전환 효과는 후속 검증 대상입니다. 근거 backend/app/discovery_evidence.json, ai-pipeline/pipeline.py, backend/app/discovery.py.

## 6. 구매의도 모델의 평가와 적용 판단 · 40초

구매의도 자료에서는 로지스틱 회귀와 LightGBM을 비교했습니다. PageValues, BounceRates, ExitRates 등은 제외하고 여덟 특징을 썼으며, 같은 특징 그룹이 분할 사이에 겹치지 않게 했습니다. 검증 AP로 선택된 모델은 LightGBM이지만 최종 평가 AP는 로지스틱 회귀가 더 높았습니다. 종료 시점 집계로 학습했기 때문에 진행 중 사용자의 구매 확률로 해석하려면 시점별 로그와 별도 검증이 필요합니다. 현재 제품에는 사용자가 고른 기준 안내와 단가 비교 CTA를 적용했습니다. 근거 ai-pipeline/artifacts/evaluation.json. 분할 7,219 / 2,365 / 2,746.

## 7. 외부 데이터와 현재 정보의 갱신 · 45초

제공 자료의 분석을 서비스 도메인으로 연결하기 위해 판매처와 공공자료를 추가했습니다. 확보 범위는 공식몰 공구 한 건과 일반 판매 비교 한 건, 공공 안내 요약 다섯 건입니다. 판매처는 여섯 시간마다 갱신하고 확인한 지 하루가 지난 정보는 만료 기준을 적용합니다. 실제로 공구 가격이 109,000원에서 129,000원으로 바뀌어 일반 판매와의 차이가 15.5%에서 0%로 갱신된 기록이 있습니다. 공공 지식의 검토일과 DB의 요청 시점 조회를 각각 표시합니다. 근거 backend/app/external_knowledge.json, scripts/collect-external-groupbuys.py, artifacts/community-20261109/live-api.json.

## 8. RAG와 권한 기반 DB 조회 설계 · 50초

챗봇은 질문과 현재 로그인 상태를 확인한 뒤 두 종류의 근거를 가져옵니다. 공식 안내는 공개 문서 검색에서 찾고, 현재 공구나 본인 저장은 허용된 도구로 DB를 조회합니다. Qwen3-1.7B는 이 근거를 선택하고 답변을 구성하는 데 사용합니다. 작은 모델을 선택해 기존 GPU 자원 안에서 운영하고, 정확한 가격과 회원 권한은 서버와 도구가 담당하도록 했습니다. 생성 후에는 출처와 응답 상태를 확인합니다. 근거가 부족하거나 의료 판단이 필요한 질문, 도구 실패에는 보류나 오류 안내를 제공합니다. 원문 갱신이 필요한 정보에는 확인 시각을 함께 제시합니다. 근거 docs/build/release-20261106/COMMUNITY-ASSISTANT.md.

## 9. Opik 품질 관측과 고정 평가 · 40초

Opik은 어느 단계에서 지연이나 실패가 생기는지 확인하기 위해 사용합니다. 고정 평가 snapshot08에서 회귀 항목 52개가 통과했고, 지원 가능한 모델 답변 36개와 공개 인용 42개를 확인했습니다. 검색 Recall@5는 원래 정답 기준 0.9444를 보존했습니다. 같은 문제로 반복 보완한 회귀 평가이므로 새로운 질문에서의 일반화 성능은 독립 평가로 확인해야 합니다. 운영에는 단계별 수치와 공개 출처 식별값을 기록하고 질문·답변 원문 및 회원 식별값의 전송은 제한합니다. 예열 모델 지연과 사용자가 경험하는 전체 응답 지연은 각각 관측합니다.

## 10. 커뮤니티 화면에서 바로 여는 챗봇 · 35초

## 11. 실제 휴대폰으로 확인한 앱·웹 연동 · 40초

같은 카카오 계정으로 로그인한 실제 기기에서 저장의 양방향 동작을 확인했습니다. 먼저 웹에서 맘큐 기저귀·물티슈를 저장하고 휴대폰 앱의 저장 목록에 나타나는 것을 확인했습니다. 이어 앱에서 저장을 해제한 뒤 웹을 다시 조회했을 때 목록에서 사라졌습니다. 이 확인은 실제 설치된 0.6.7 앱으로 수행했고 시험용 저장은 복구했습니다. 계정은 provider와 subject로 연결하고, 앱과 웹은 동일한 API와 DB를 조회합니다. 닉네임도 같은 계정으로 표시됨을 확인했습니다.

## 12. 배포 구조와 DB 책임 · 40초

웹은 React와 Vite, 앱은 Android 패키지로 같은 서비스 API를 사용합니다. 공개 HTTPS 요청은 Cloudflare를 거쳐 FastAPI로 전달되고 데이터는 Neon PostgreSQL에 저장됩니다. 현재 API와 모델 운영 환경은 기존 Elice 서버 구성입니다. 물리 테이블은 users, tokens, records, rate_buckets 네 개입니다. 글과 댓글, 저장 같은 논리 엔터티는 records의 kind와 JSON 데이터로 표현합니다. 따라서 부모 대상의 종류와 접근 권한, 삭제 정리는 API가 검사합니다. 고유 키와 revision, 트랜잭션으로 반복 요청과 충돌을 처리합니다. 근거 backend/app/db.py, release.py, social_auth.py.

## 예상 질문과 답변

- 제공 데이터를 어디에 썼나? 소비자 자료는 비교 기준 선택, 거래 자료는 중복 감사와 공동 저장 조합 분석, 종료 세션은 모델 비교와 CTA 적용 조건 검토에 사용했다. 4~6장이 근거다.
- 왜 LightGBM 점수로 실시간 구매를 예측하지 않았나? 학습 자료는 종료 세션이고 현재 이용자의 예측 시점과 다르다. 현재는 선택 기준 안내를 운영하며, 시점별 로그와 시간순 평가를 확보한 뒤 적용을 판단한다.
- 연관 분석 성능 36.21%는 무엇인가? 조건을 충족한 과거 평가 송장에서 숨긴 품목을 상위 5개 추천에 복원한 비율이다. 운영 커뮤니티에는 공동 저장 방법을 적용했다.
- RAG에서 실시간 데이터는 어디인가? 공개 자료에는 검토일을 붙이고 현재 공구·본인 활동은 권한을 검사한 DB 도구로 요청 시점에 조회한다.
- Opik으로 무엇을 개선하나? 검색·도구·생성·검증 단계별 오류와 지연, 출처 버전을 확인하고 고정 회귀 평가와 새로운 질문 평가에 활용한다.
- DB가 왜 테이블 4개인가? 논리 엔터티는 records.kind와 JSON으로 관리한다. 부모 종류·권한·삭제 정리는 API 책임이며, 고유 키·revision·트랜잭션으로 일관성을 검사한다. 상세 ERD는 24~26장이다.
- 외부 자료를 얼마나 모았나? 확인된 범위는 공식몰 공구 1건과 비교 1건, 공공 안내 요약 5건이다. 확인 시각과 유효기간을 표시하고 확보 범위를 단계적으로 넓힌다.
- 실제 서비스 효과는 검증했나? 구현과 실기기 저장 왕복, 고정 모델 평가를 확인했다. 실제 이용 효과는 질문 해결률·비교 사용률·저장률을 정의하고 동의 기반 표본에서 측정할 계획이다.
