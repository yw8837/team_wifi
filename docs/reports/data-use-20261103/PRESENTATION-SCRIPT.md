## 2 제공 데이터와 적용 범위

예정 40초

정량 자료는 네 종류입니다. 소비자 1,000명의 응답, 거래 CSV, 두 해의 소매 거래, 완료된 쇼핑 세션입니다. 각 자료의 사람과 상품, 세션은 현재 앱 계정과 연결되지 않습니다. 따라서 행을 모두 더하거나 공개 고객 ID를 앱 회원에 붙이지 않았습니다. 회사 문서는 서비스 요구사항을 파악하는 데 활용했습니다.

## 3 할인 민감도는 한 가지로 모이지 않았습니다

예정 50초

D1에서는 매우 민감한 사람이 35%, 어느 정도 민감한 사람이 31.9%, 민감하지 않은 사람이 33.1%였습니다. Baby Products 표본은 41명뿐이므로 국내 육아 고객을 대표한다고 보지 않았습니다. 이 차이를 설계 참고로 삼아 가격만 강요하지 않고 관심 분야와 비교 기준을 직접 선택하도록 만들었습니다. 현재 추천은 이 명시적 선택을 따르는 규칙입니다.

근거: backend/app/discovery_evidence.json d1; backend/app/discovery.py; https://www.kaggle.com/datasets/salahuddinahmedshuvo/ecommerce-consumer-behavior-analysis-data

## 4 D2의 모든 거래가 D3에 포함됐습니다

예정 35초

CSV의 추가 index를 빼고 업무열 8개의 값과 반복 횟수를 비교했습니다. D2의 541,909행 모두 D3 두 번째 시트에 있었고, D3에는 운송료 1행이 더 있었습니다. 그래서 둘을 합쳐 거래량을 부풀리지 않고 D3를 분석 기준으로 삼았습니다. 서비스의 저장과 관심도 같은 계정의 반복 행동을 성과로 중복 계산하지 않도록 구현했습니다.

근거: ai-pipeline/artifacts/overlap_audit.json; ai-pipeline/pipeline.py canonical/retail; backend/app/release.py service_insights

## 5 동시구매 분석을 공동 저장 집계에 적용했습니다

예정 65초

D3에서는 송장을 시간순으로 나눴습니다. 앞의 28,947개에서 품목 간 규칙을 만들고 뒤의 7,237개 중 조건을 충족한 4,338개를 평가했습니다. 품목 하나를 숨기고 나머지를 알고 있을 때 상위 다섯 개로 복원한 비율은 규칙이 36.21%, 인기순이 10.56%였습니다. 이는 과거 거래의 조건부 평가입니다. 앱에는 품목을 함께 선택한 집계를 활용해 5계정 이상이 함께 저장한 육아템과 양방향 비율을 운영자에게 보여줍니다. 해외 상품 모델을 육아 상품으로 바꾸거나 저장을 주문으로 부르지 않았습니다.

근거: backend/app/discovery_evidence.json d3.bundle_evaluation; ai-pipeline/pipeline.py; backend/app/release.py:141; https://archive.ics.uci.edu/dataset/502/online+retail+ii

## 6 구매 여부 분류는 연구 범위로 보존했습니다

예정 55초

D4는 완료된 방문 세션 12,330개이며 구매 세션 비율은 15.47%입니다. 중복 특징을 한 그룹에 묶어 분할하고 검증 AP로 LightGBM을 선택했습니다. 평가 AUROC는 0.745, AP는 0.294입니다. 평가 AP만 보면 로지스틱 회귀가 더 높아서 모든 지표에서 최고라고 말할 수 없습니다. 체류시간은 세션이 끝난 값이라 지금 접속 중인 사람의 구매 의도로 쓰기 어렵습니다. 앱에는 자동 구매 점수 대신 직접 고른 비교 기준과 단가 비교 안내를 적용했습니다.

근거: ai-pipeline/artifacts/evaluation.json; backend/app/discovery_evidence.json d4; https://archive.ics.uci.edu/dataset/468/online+shoppers+purchasing+intention+dataset

## 7 서비스 시연 경로

예정 100초

먼저 마이페이지의 관심 육아템 설정을 엽니다. 관심 분야와 비교 기준을 저장한 뒤 홈으로 돌아오면 내 관심 육아템과 이유가 나타납니다. 다음으로 운영자 계정의 육아템 관심 분석을 열어 카테고리별 고유 계정 집계, 함께 저장한 조합, 제공 자료의 근거를 보여줍니다. 조합이 없으면 5계정 기준을 충족하지 않았다는 설명을 보여주면 됩니다. 발표용 운영 데이터나 성과를 만들지 않습니다. 화면에 제시한 예시는 격리된 기능 검증 화면이며 운영 고객의 성과가 아닙니다.

근거: frontend/src/discovery.tsx; artifacts/service-data-20261102/interest-home-mobile.png; https://moduyuga.onrender.com/my/preferences; https://moduyuga.onrender.com/admin/insights

## 8 실제 서비스 효과를 검증할 측정을 구현했습니다

예정 45초

마지막으로 실제 서비스의 효과를 측정할 수 있도록 노출, 클릭, 저장과 관심 완료를 연결했습니다. 화면의 절반이 1초 이상 보인 경우를 노출로 삼고, 선택 동의한 일반 회원만 최근 30일의 고유 계정 기준으로 집계합니다. 소수 표본은 숨기고 신뢰구간과 판단 보류를 표시합니다. 현재까지 확인한 것은 분석과 기능 구현입니다. 전환율이나 매출 상승은 앞으로 실제 데이터와 별도 비교 실험으로 검증해야 합니다.

## 예상 질문과 답변

**앱 추천은 학습 모델인가요?** 현재 홈은 명시한 관심 분야와 저장 이력의 규칙 기반 목록입니다. 제공 데이터는 설계 근거와 연구 실험, 집계 방법의 적용에 사용했습니다.

**왜 5명 이상인가요?** 소수 집계 노출을 줄이기 위한 운영 정책입니다. 통계적 유의성이나 익명성을 자동 보장하는 임계값은 아닙니다.

**Recall@5 36.21%는 구매율인가요?** 아닙니다. 조건을 충족한 과거 송장에서 숨긴 1개 품목을 상위 5개로 복원한 비율입니다.

**왜 LightGBM을 골랐나요?** 사전에 정한 검증 AP가 더 높았습니다. 평가 AP는 로지스틱 회귀가 높으므로 모든 지표에서 최고라고 주장하지 않습니다.

**성과가 증가했나요?** 기능과 측정 기반을 구현했습니다. 실제 전환율, 매출, 검색 또는 AI 인용 개선은 아직 검증하지 않았습니다.

**앱에서도 바로 보이나요?** 최신 코드의 웹은 반영됐고 Android 서명본을 만들었습니다. 기존 설치본의 새 화면에는 앱 업데이트가 필요하며 최신 파일은 아직 Play에 올리지 않았습니다.

**화면설계서의 채팅 추천과 결제까지 구현됐나요?** 설계서는 목표 서비스 범위입니다. 이 발표에서 확인한 데이터 활용 구현은 관심 설정, 규칙 기반 개인화, 공동 저장 분석과 활동 측정입니다. 대화형 추천과 실제 주문·결제 등의 완료 증거를 대신하지 않습니다. [제공 설계 자료와 현재 적용 대조](DESIGN-REFERENCE.md)를 참고합니다.

## 시연 준비

운영자 계정은 미리 로그인합니다. 관심 설정 시연은 발표용으로 허용된 계정을 사용하고, 이전 설정을 기록해 둡니다. 운영 분석은 읽기만 합니다. 5계정 조합이 없으면 빈 상태와 집계 기준을 설명합니다. 무료 서버 지연에 대비해 격리 검증 화면을 준비하되 합성 계정의 숫자를 실제 고객 성과로 설명하지 않습니다. 실시간 시연이 길어지면 7번 슬라이드의 준비 화면으로 전환합니다.
